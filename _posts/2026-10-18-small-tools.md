有一段时间，我热衷于收集工具。

每个工具看起来都能解决一个问题，合在一起却制造了新的问题：我该在哪里记笔记？这个文件应该放进哪个应用？刚才那条想法，是写在待办里，还是写在文档里？选择本身消耗的注意力，有时比事情还多。

后来我开始偏爱另一种东西：只做一件事的小工具。

## 一个工具，只做一件事

Unix 的哲学里有一句话：让每个程序只做好一件事。听起来很朴素，做起来却很难。大多数产品都希望自己变得更大、更全，最好把所有需求都装进去。结果是用起来越来越重，真正高频的功能，反而被埋进了层层菜单里。

只做一件事的工具，边界清楚。你知道它为什么存在，也知道什么时候不该用它。它不会试图猜你想干什么，更不会在打开的时候先给你看一屏推荐。

## 组合，而不是堆叠

小工具并不意味着功能弱。它只是把「组合」的权利交还给使用者。

Markdown 只管内容，不需要关心长什么样；Git 只管版本，不负责写作体验；编辑器只管输入，不替我做决定。每一件都很简单，但连在一起，就能支撑起一套稳定的工作流。

```text
Markdown 写内容  →  Git 记录变化  →  GitHub Actions 构建  →  Pages 发布
```

这种组合还有一个好处：任何一环都可以替换。哪天我想换一个编辑器，前面的文章不会受影响；哪天想换一种发布方式，内容也还是原来的 Markdown 文件。

## 判断一个工具值不值得留下

现在我的工具栏很短。每次想加入一个新东西，我通常会问自己三个问题：

- 它解决的是真问题，还是我想象出来的问题？
- 不用它，我能不能完成任务？
- 它会不会要求我改变原来的工作方式？

如果答案分别是「真」「能」「不会」，我才会考虑把它留下。否则，收藏一个工具，和读完一篇工具测评，本质上没有区别：都只是获得了一点「我好像也能做到」的错觉。

## 少一点，但好一点

我不是反对新工具。恰恰相反，好的工具会让人更愿意做事。只是工具应该像一把顺手的剪刀：拿起来就能用，用完就放下，不需要你时刻惦记它。

工具是手的延伸，不该成为注意力的主人。

现在的我，更喜欢那些安静的东西：打开很快，界面很干净，功能少到不需要教程。它们不争抢注意力，只是在需要的时候，恰好在那里。
